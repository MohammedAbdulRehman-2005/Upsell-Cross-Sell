# Requirements clarification and implementation decisions

## Explicit requirements from the assignment

1. Trigger recommendations only after an order is marked delivered.
2. Return up to six recommended products.
3. For one ordered product line, use its six mapped recommendations as the candidate source.
4. For multiple ordered product lines, distribute six recommendation slots proportionally; the brief gives two lines → three slots each as an example.
5. Do not recommend duplicate products.
6. Exclude Rx/drug products.
7. Handle unavailable products, missing mappings, duplicate recommendations, and multiple line items.
8. Provide a WhatsApp customer journey, sample orders, logic/assumptions, tests/results, setup instructions, and walkthrough.

## Finalized MVP decisions (must be stated in README/demo)

| Topic | Finalized MVP rule | Rationale / explainability |
|---|---|---|
| Allocation basis & quantity semantics | **Equal allocation for the MVP** across distinct ordered SKUs that have mappings (`base_quota = 6 // M`, `remainder = 6 % M`). `quantity_sum` is used **only** as a tie-breaker for source prioritization when **more than six** mapped source SKUs exist (`M > 6`). For `M <= 6`, `quantity_sum` is not included in `priority_key` so quantity never influences remainder allocation when all mapped sources can participate. It does **NOT** make MVP slot allocation quantity-weighted. | The source mapping workbook has no quantity column and the brief's two-line example specifies 3+3 slots. Conditional tie-breaking ensures equal allocation and remainder distribution for `M <= 6` are completely independent of quantity. |
| Repeated order lines | Aggregate identical product codes into one distinct source SKU; retain `quantity_sum` and earliest `first_line_index` | Avoids giving one SKU multiple base quotas simply because it appears on multiple lines, while preserving `quantity_sum` for `M > 6` source prioritization tie-breaking and for audit traces. |
| Deterministic & explainable source prioritization | All mapped source products undergo consistent candidate eligibility evaluation before prioritization, and are then ranked by a conditional deterministic `priority_key`:<ul><li>**For `M <= 6`**: `(-eligible_candidate_count, first_line_index, product_code)` (`eligible_candidate_count` desc, `first_line_index` asc, `product_code` asc).</li><li>**For `M > 6`**: `(-eligible_candidate_count, -quantity_sum, first_line_index, product_code)` (`eligible_candidate_count` desc, `quantity_sum` desc, `first_line_index` asc, `product_code` asc).</li></ul>Preserve recommendation provenance (`source_product_code` and original `mapping_rank`) in the decision trace. | Ensures quantity does not influence remainder allocation when all mapped sources can participate (`M <= 6`), while still providing an explainable quantity tie-breaker when selecting among `M > 6` mapped sources. |
| 1–6 mapped source SKUs (`M <= 6`) | Each mapped source receives `base_quota = 6 // M` slots; the first `remainder = 6 % M` sources in `M <= 6` priority order `(-eligible_candidate_count, first_line_index, product_code)` receive +1 slot | Ensures exact 6-slot equal allocation (e.g., 1→6; 2→3,3; 3→2,2,2; 4→2,2,1,1; 5→2,1,1,1,1; 6→1,1,1,1,1,1) without quantity influencing remainder slots. |
| More than 6 mapped source SKUs (`M > 6`) | **No arbitrary first-six truncation.** All `M` mapped sources undergo consistent eligibility evaluation and are ranked via the `M > 6` priority order `(-eligible_candidate_count, -quantity_sum, first_line_index, product_code)` (`base_quota = 0`, `remainder = 6`). The top 6 prioritized sources receive 1 initial quota slot each, and **all `M` mapped sources** participate in round-robin backfill in priority order | Prevents arbitrary order-line position truncation when a customer orders >6 mapped products; `quantity_sum` acts only as a tie-breaker when `M > 6` and `eligible_candidate_count` is tied, and every mapped source remains eligible during backfill. |
| Missing mapping | Ignore unmapped source lines; allocate slots equally across the remaining `M` mapped source lines | Partial mapping coverage must not suppress valid recommendations. If `M = 0` (no ordered SKU has a mapping), return an empty recommendation list (`NO_MAPPED_SOURCE`) and do not send a WhatsApp message. |
| Already purchased products | Exclude every SKU present in the current order before candidate selection | Never upsell or cross-sell an item the customer just received in the same order. |
| Duplicate candidates across sources | Keep the first accepted occurrence under deterministic source priority and ascending mapping rank (1–6); never recommend the same SKU twice | Stable and reproducible deduplication with full source and rank provenance (`source_product_code`, `mapping_rank`, `selection_phase`) in the decision trace. |
| Backfill | If a source cannot fill its initial quota (due to purchased/Rx/inactive/out-of-stock/duplicate exclusions), scan its remaining ranked candidates (1–6); if total accepted candidates after the initial quota pass is still `< 6`, perform a global round-robin backfill across **all `M` mapped sources** in deterministic source priority order | Preserves proportional per-source representation first, then fills spare capacity exclusively from valid mapped candidates of the ordered products while preserving `source_product_code` and original `mapping_rank`. |
| Return fewer than six when exhausted | **Return fewer than six** (0–5) whenever the union of unique eligible mapped candidates is `< 6`; if 0 remain, return `NO_ELIGIBLE_CANDIDATES` and suppress WhatsApp dispatch | "Up to six" is a strict ceiling. Because the dataset forms 10 **isolated mapping clusters** of 7 SKUs each (the workbook establishes recommendation graph structure, not actual product category membership), multi-item orders within the same isolated mapping cluster naturally have `< 6` non-purchased targets (e.g., 2 items in the same cluster leave at most 5 targets). Never relax Rx, stock, active, or purchased filters to pad to six. |
| Global bestseller fallback | **Future enhancement only (not enabled in MVP)** | Recommendations in the MVP must strictly originate from the ordered products' mapped candidates so every recommendation has direct co-purchase provenance. |
| Rx exclusion | Require explicit catalogue metadata `is_rx = false`; `is_rx = true` or missing/unknown Rx metadata is excluded (fail closed) | Workbook does not include category/Rx metadata; never infer safety-critical Rx status from product-name text. |
| Availability & active status | Require explicit catalogue metadata `is_active = true` and `available_quantity > 0`; inactive, out-of-stock, or unknown items fail closed | Workbook does not include inventory. Prototype supplies explicit catalogue metadata fixtures to test stock and active filtering deterministically. |
| Mapping positions | Treat positions 1–6 as ordinal co-purchase relevance ranks, lower rank first (rank 1 = highest relevance) | Positions are ordinal ranks, not raw co-purchase counts or probabilities. |
| WhatsApp provider & failure semantics | **Meta WhatsApp Cloud API is the primary provider; the WhatsApp simulator is the fallback/demo provider.** Do **not** automatically switch to the simulator after a real Meta API delivery failure (which would create a false impression that the customer received a message).<ul><li>**Explicit simulator mode or unavailable credentials**: simulator can be selected.</li><li>**Meta API transient failure**: retry safely and record the failure/pending state.</li><li>**Meta API acceptance**: record provider acceptance (`PROVIDER_ACCEPTED`), not confirmed delivery.</li><li>**Actual delivery confirmation**: use Meta webhook status updates (`DELIVERED`).</li></ul> | Prevents silent false-positive deliveries when the live primary provider fails, while clearly distinguishing API acceptance from asynchronous webhook delivery confirmation and supporting deterministic simulator runs when credentials are unconfigured or simulator mode is explicitly selected. |
| Trigger reliability | Validate `ORDER_DELIVERED` event and authoritative `DELIVERED` order status; enforce idempotency key per `(order_id, campaign_type)` | Prevents premature recommendations and guarantees duplicate webhook deliveries are idempotent no-ops (`ALREADY_DISPATCHED`). |
| Consent / opt-out | Enforce customer messaging consent (`has_consent = true` and `opted_out = false`) before WhatsApp dispatch | Business-initiated WhatsApp utility/marketing messages require explicit opt-in compliance. |

## Resolved design questions (formerly open assumptions)

1. **Equal vs. quantity-weighted allocation**: Finalized as **equal allocation for the MVP** across distinct mapped SKUs. `quantity_sum` is used **only** as a tie-breaker for source prioritization when `M > 6` mapped source SKUs exist; for `M <= 6`, `quantity_sum` is excluded from `priority_key` so quantity never influences remainder allocation when all mapped sources can participate. It does **not** make MVP slot allocation quantity-weighted.
2. **Orders with more than six mapped SKUs (`M > 6`)**: Finalized as **no arbitrary first-six truncation**. All `M` mapped sources undergo consistent eligibility evaluation before prioritization and are sorted by the conditional deterministic priority ordering: `(-eligible_candidate_count, first_line_index, product_code)` for `M <= 6`, and `(-eligible_candidate_count, -quantity_sum, first_line_index, product_code)` for `M > 6`, granting 1 initial slot to each of the top 6 prioritized sources when `M > 6` and including all `M` sources in round-robin backfill while preserving `source_product_code` and original `mapping_rank` in the decision trace.
3. **Repeated occurrences of the same SKU**: Aggregated into a single distinct source SKU with summed quantity (`quantity_sum`) and earliest `first_line_index`.
4. **Catalogue metadata & dataset graph topology**: Supplied via an explicit catalogue metadata store (`is_rx`, `is_active`, `available_quantity`, price) with strict fail-closed semantics when metadata is missing. The source workbook establishes 10 **isolated mapping clusters** of 7 SKUs each (recommendation graph structure, not actual product category membership).
5. **Exhausted candidate pool (`< 6` eligible targets)**: Finalized to **return fewer than six** valid recommendations without relaxing any filter. **Global bestseller fallback is a future enhancement only.**
6. **WhatsApp provider & failure semantics**: Finalized with **Meta WhatsApp Cloud API as the primary provider** and the **WhatsApp simulator as the fallback/demo provider**. The simulator is selected only when explicitly in simulator mode or when Meta credentials are unavailable—never as an automatic failover after a real Meta API delivery failure. Meta API transient failures are retried safely and recorded as failed/pending; Meta API acceptance records provider acceptance (not confirmed delivery); actual delivery confirmation is recorded via Meta webhook status updates.

## Future enhancements (post-MVP roadmap)

- **Global bestseller fallback (future enhancement only)**: Optional opt-in policy to pad recommendations from curated non-Rx in-stock bestsellers when mapped candidates yield fewer than six items, clearly tagged with `selection_phase = "GLOBAL_FALLBACK"`. Excluded from MVP to keep all recommendations strictly grounded in the mapping table.
- **Quantity-weighted or revenue-weighted slot allocation**: Optional weighting mode for B2B or high-quantity repeat orders.
- **Live OMS / ERP inventory & Customer Data Platform (CDP) sync**: Real-time webhook and inventory reservation integration.
- **Historical order-window suppression**: Excluding non-consumable products purchased in recent prior orders in addition to current-order exclusions.
